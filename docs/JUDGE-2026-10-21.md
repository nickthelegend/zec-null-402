## Findings with evidence

### Security

1. **Unlimited double spend through non-canonical nullifiers (critical).**
   `packages/gateway/src/gateway.ts:118` checks `this.state.nullifiers[s.nullifier]` with the string
   exactly as sent, and `:122` stores it under that string. `packages/circuits/src/index.ts:113` hands
   the strings to `snarkjs.groth16.verify`, which parses `"0123"` and `"0x7b"` to the same field
   element. So after a call is paid with nullifier `n`, the same proof pays again with `"0"+n`,
   `"00"+n`, `"0x…"`, each a fresh key. The `NULLIFIER_SPENT` refusal the README advertises only
   holds for byte-identical replays.
2. **Concurrent redeem double spend.** `gateway.ts:112-124`: the challenge lookup (`:113`) and the
   nullifier check (`:118`) happen before `await verifyOffChain` (`:119`); the nullifier is written only
   after it (`:122`). Two requests carrying the same payment, sent together, both pass every check and
   both get 200.
3. **Relay attack on the client.** `packages/sdk/src/index.ts:92-107`: `pay(url)` proves whatever
   `zec-null-402` challenge any server returns, without checking that the URL is on the client's own
   gateway, that `resource` is the path it asked for, or that `payTo` is the gateway's. A server the
   agent is pointed at (the MCP `pay` tool takes any URL, `packages/mcp/src/tools.ts:87`) can fetch a
   real challenge from the gateway, pass it on, and redeem the agent's proof for its own request. The
   agent's note is burned for the attacker.
4. **Unauthenticated, wallet-spending `POST /api/anchor`.** `gateway.ts:175` runs `anchor()`, which
   sends 10,000 zat from the gateway wallet (`packages/gateway/src/serve.ts:22`), for any caller. The
   server sends `access-control-allow-origin: *` (`gateway.ts:148`) and a body-less POST is a CORS
   simple request, so any web page open on the operator's machine can drain the wallet 10,000 zat at
   a time.
5. **Concurrent claim double credit.** `gateway.ts:78` checks `deposits[txid]` before the
   multi-second `await scan(...)` (`:81`) and records the deposit only after it (`:88`). Two
   concurrent claims both append the notes. No value is created (the duplicate leaves share
   nullifiers), but the README's "a deposit is credited once" and the leaf count in anchors are wrong
   after it.
6. **The gateway's incoming viewing key is served to anyone.** `gateway.ts:159` returns
   `depositUivk` from `GET /api/info`. No client needs it, and with it anyone sees every deposit's
   amount, memo commitment and time. The docs' "who sees what" table
   (`packages/docs/README.md:41`) says the chain does not learn amounts or memos.
7. **Unbounded memory.** `gateway.ts:56,107`: every unpaid `GET` adds a challenge that is never
   removed unless paid (expired ones stay). `gateway.ts:149-153`: request bodies are read with no
   size limit.

## One bold idea

**Prove only against anchored roots.** Let the client refuse to prove against any root that is not in
an on-chain anchor it has read itself with the anchor viewing key (the Rust scanner already reads
memos). Every client then proves against the same public root, so a gateway cannot partition users
by root, and a gateway that shows two clients different histories has to put both on-chain, where
anyone can see the fork. The cost is latency for new notes (spendable after the next anchor), which
fits Kippu's "prepay, then spend for days" shape. That turns "the gateway is trusted for privacy" into
"the gateway is trusted for liveness only".
