ZCASHPrepaid ZK tickets for APIs

One deposit. A ticket per call.

Pay once with a shielded Zcash deposit, then pay each API call with a zero-knowledge proof of one prepaid note. No transaction and no block wait per call, and a gateway that follows the protocol learns that some note paid, not which.

How it works

Zcash has no contracts, so the gateway is the pool.

null-402's on-chain verifier can't be ported to Zcash. Kippu keeps the deposit and the audit trail on-chain and moves the per-call check to the gateway, in the open.

  1. 01

    Print notes

    The client makes N notes and one commitment over their secret hashes and values. Secrets stay in a 0600 file.

  2. 02

    Deposit once

    One shielded transaction to the gateway with memo z402:<commitment>. The gateway's viewing key checks amount and memo before crediting, once.

  3. 03

    Prove per call

    402 → the client reads the named anchor on-chain itself, then proves it holds an unspent note under that anchored root, bound to this exact request → the gateway verifies the Groth16 proof and burns the nullifier.

  4. 04

    Anchor

    The gateway writes its root and nullifier-set hash in a shielded memo (a0992237…), readable with a published viewing key. Clients prove only against a recent anchored root, so everyone proves against the same one.

Voided in the live run

Seven tickets the gateway would not honour.

Each was tried against the testnet run of Oct 20. The code is the gateway's own answer.

  • VOIDNULLIFIER_SPENT

    A paid proof sent again for a new request.

  • VOIDNULLIFIER_SPENT

    The second fixture note's proof replayed.

  • VOIDNOT_BOUND_TO_CHALLENGE

    The amount in the public signals changed.

  • VOIDNOT_BOUND_TO_CHALLENGE

    A proof made for one request sent for another.

  • VOIDBAD_PROOF

    The nullifier changed, claiming a different note.

  • VOID409 already claimed

    The same deposit claimed a second time.

  • VOIDMEMO_MISMATCH

    A claim with one note's value altered, on a fresh gateway.

Fixed on Oct 21

A review found two ways to pay twice. Both are closed.

  • A spent note's nullifier written 0<n> or in hex: now MALFORMED_SIGNALS.
  • One payment sent several times at once: now paid once.
  • A server relaying the gateway's challenge: the client refuses to prove.
  • Anchoring over HTTP: needs the operator's token.

Tested against a fresh gateway on testnet with real proofs, not part of the Oct 20 run. The review.

Fixed on Oct 22

A gateway can no longer hand each client its own root.

  • A root with no on-chain anchor: the client won't prove (UNANCHORED_ROOT).
  • A per-client root passed off as the real anchor: ANCHOR_MISMATCH.
  • An anchor older than 2,880 blocks: ANCHOR_TOO_OLD.
  • A restart keeps challenges and spent nullifiers; two gateway processes on one database pay a note once.

The client reads the anchor from lightwalletd with the published anchor key before it proves. Tested against dishonest gateways in front of a real one, with real proofs.

Read the back of the ticket

Conditions of carriage.

What a ticket hides, and who you still trust.

  1. The gateway is trusted for liveness and its nullifier set. Clients check its anchored root before every proof; its spent set is checkable only after the fact.
  2. Roots are anchored, addresses are not. A gateway would have to put a per-client root on-chain, where the published anchor key shows it; clients don't yet scan for competing anchors. It still sees each caller's network address.
  3. New notes wait for an anchor. A deposit pays once the gateway's next anchor is mined, about a block with auto-anchoring.
  4. The anonymity set is the credited notes. In the run there was one depositor, so every call came from that depositor's notes.
  5. No change. A note pays one call of its full value; a dearer endpoint needs a note of its own price.
  6. The demo viewing key is public. It is published so a fresh clone can re-check the real deposit; for this deployment anyone can read the deposit's amount and memo.
  7. Single-party Groth16 setup. Whoever ran it could forge proofs; a real deployment needs a ceremony.
  8. Testnet only, not audited. A portfolio piece; the Zecathon entry is Kage (Shielded x402).
